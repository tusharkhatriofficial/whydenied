## One line

WhyDenied turns AWS `AccessDenied` errors into reviewed pull requests against your Terraform, granting exactly the missing permission and nothing more.

## The problem

Least privilege is the rule everyone agrees with and few teams sustain. Every new feature, renamed resource or environment difference produces a fresh `AccessDenied`. Fixing one properly means reading the error, working out which policy blocked it, finding the Terraform file that defines the role, and opening a pull request. That is 30 to 60 minutes of an engineer's time.

Under deadline pressure people take the two shortcuts that cause real damage. They fix it by hand in the AWS console, so the live role no longer matches the code and the next `terraform apply` silently reverts it. Or they grant `"Action": "*"` to make the error go away, and the role keeps that access forever.

The errors also appear where nobody is watching, in Lambda logs, CI output and cron jobs, so the same denial repeats hundreds of times before anyone notices.

## What it does

1. An EventBridge rule receives every `AccessDenied` and `UnauthorizedOperation` event that CloudTrail records, including read-only calls.
2. A Lambda function identifies the IAM role (not the temporary session), the action, the resource and the reason AWS gave.
3. DynamoDB stores one item per (role, action, resource) with a count, so 500 identical failures become one issue.
4. WhyDenied finds the `aws_iam_role` in the team's Terraform repository and opens a pull request adding an inline policy for that one action on that one resource.
5. An AI model writes review notes for the reviewer: whether the access looks expected, the risk of granting it, and what to check.
6. Slack or Discord receives one alert with a link to the pull request.

A human reviews and merges. WhyDenied never modifies IAM itself.

The effect is that roles can start with minimal permissions and grow one reviewed, exact permission at a time, which makes least privilege practical instead of aspirational.

## How AWS is used

| Service | Role in the project |
|---|---|
| CloudTrail | Source of denial events |
| EventBridge | Rule matching `AccessDenied` and `UnauthorizedOperation`, including read-only management events |
| Lambda | Analyzer (Python 3.14, arm64) and the public API behind the setup page |
| DynamoDB | Denial records, deduplication, status and pull request links |
| SSM Parameter Store | SecureString storage for the GitHub token, AI key and webhooks |
| Bedrock | Optional provider for the AI review notes |
| API Gateway | HTTP API for the setup page, rate limited |
| Amplify Hosting | The live setup page |
| S3 and CloudFormation | Public packaged template for one-click install |
| SAM | The whole stack defined as code |

WhyDenied is self-hosted: it runs in the user's own account, so CloudTrail data, IAM details and tokens never leave it.

## Safety

- The fix is generated by code, not by the model. The model writes review notes only, so a wrong or manipulated answer cannot widen permissions.
- Each fix grants one action on one resource. Wildcard actions are refused.
- Only a missing `Allow` in an identity-based policy is fixed automatically. Explicit denies, SCPs, permissions boundaries and session policies are reported for a human.
- Event data reaches the model as delimited data, and the model's output is validated and stripped of markup before it reaches a pull request.
- The analyzer can read only SSM parameters under `/whydenied/` and write only to its own table.
- A conditional DynamoDB update means only one invocation can open a pull request for a given denial, and retries reuse the existing branch.

## What I learned

- **EventBridge drops read-only denials by default.** CloudTrail records a denied `Get`, `List` or `Describe`, but a rule only receives it when its state is `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS`. I found this by testing `dynamodb:ListTables` against `sqs:CreateQueue` before writing any feature code: the write arrived, the read did not. Without the opt-in, WhyDenied would miss about half of real denials.
- **Delivery takes about 20 to 25 seconds,** measured on both calls, which is what makes a live demo possible.
- **Data events are a real boundary.** S3 `GetObject` and DynamoDB `GetItem` denials need CloudTrail data event logging, which is billed separately, so the demo uses a management event.
- **Some AWS error messages are inconsistent.** SQS reports the action as `sqs:createqueue`, so the action is rebuilt from `eventSource` and `eventName` instead of parsed from the message.
- **Doing the fix in code rather than with the model turned out better.** For a missing `Allow`, the required policy is fully determined by the event, so a template produces it exactly and can never invent a wildcard. It also meant the project kept working while Bedrock was unavailable on my account, with the model reduced to the part it is actually good at, explaining the change to a reviewer.
- **Account limits are part of engineering.** Bedrock returned `Operation not allowed` for every model on this new AWS India account, so I made the provider switchable and shipped with OpenAI while the support case is open. `AIProvider=bedrock` is one parameter away.

## Limitations

- Management events only; data events need separate CloudTrail logging.
- One region, one account and one repository per deployment.
- Terraform only, matching roles by an explicit `name`. CloudFormation and CDK are not supported yet.
- Identity-based policies only; other denial types are reported, not fixed.

## Try it without deploying

The setup page runs the real parser and fix generator on Lambda. Paste any `AccessDenied` error and it returns the parsed denial and the Terraform it would propose. It also checks any public Terraform repository and reports which roles it can match, and it shows live denials from the demo account.
